# 交易结构算盘

**同一笔交易，换一种付法，资金、股权和稀释会怎么变？**

把增资、老股、现金和股份放进同一把尺子里复算，让资金去了哪里、股份发给了谁、交割后各方还剩多少一眼能看明白。一次使用会得到资金去向、股权发生了什么变化、融资缺口和下一步，不用先搭一套完整并购模型。

这是交易早期的结构情景计算器。它只机械复算用户确认的输入，不替用户确定价格，不表示交易能够取得控制权或完成审批，也不出具法律意见、税务意见或会计结论。

## 什么时候使用

以下任务直接使用：

- “投前估值六亿元，增资一亿元，投资人投后占多少？”
- “买20%老股再增资一亿元，交割后合计持股是多少？”
- “五亿元对价，四成现金、六成股份，要发多少股？”
- “换一种支付方式，现金压力和原股东稀释会怎么变化？”
- “现有资金够不够，还差多少融资？”

以下任务转向相邻产品：

- 财务指标和倍数尚未形成价格区间，转入「估值区间快算」；
- 需要核对股本分母、股东名册或历史股份变动，转入「股权表核验」；
- 交易方案已经确定，只需要画出交易结构图，转入「交易结构图」；
- 需要完整交易建议、每股收益增厚摊薄、购买价格分摊、协同效应、审批路径或正式交付，转入「MAI Lab并购Agent」。

## 首版支持的五种情景

1. **增资**：计算投后估值、新投资人持股和原股东稀释；
2. **老股转让**：计算买方取得持股、卖方剩余持股和老股对价；
3. **增资加老股转让**：分开计算公司取得的增资款、卖方取得的老股对价和买方交割后合计持股；
4. **现金加股份支付**：拆分现金对价与股份对价，计算新发行股份和买方原股东稀释；
5. **纯股份支付**：计算全部以股份支付时的新发行股份和卖方取得买方持股。

首版不计算可转换债券、业绩承诺、分期收购、购买价格分摊、每股收益增厚摊薄或协同效应，不自动判断监管阈值。

## 最低输入

先确认交易情景、测算日期、币种、金额单位和数据来源。不同情景再补充：

- 增资：投前估值和增资金额；
- 老股转让：交易前完全稀释总股本、卖方交易前持股、受让股份、每股价格或老股总对价；
- 增资加老股：投前估值、增资金额、受让老股比例和老股总对价；
- 现金与股份支付：交易总对价、现金支付比例、买方交易前总股本和买方参考股价；
- 资金缺口：已确认的可用现金、债务融资、股权融资或其他资金。

所有股权比例使用同一估值时点、同一币种、同一金额单位和完全稀释口径。用户不知道的内容可以标为“暂不明确”；关键分母缺失时不生成看似精确的结果。

## 本地计算

### 直接调用速查

下面是完整的合法模式与参数。已有对应示例时直接运行，不先调用 `--help`、搜索源码或猜 `primary` / `secondary` 等不存在的模式。每个情景一次计算，发现输入错误后才针对性重试。

所有股份参数按**实际股数（股）**传入；不能把 1000 万股传成 1000。涉及每股价格时，金额统一换算为元，使用 `--unit 元`，每股价格按元/股；在给用户的结果中再换回万元或万股。收到单位错误，应修正输入后重算，不能称为脚本显示问题。

| 中文任务 | `--mode` | 必填的计算参数 |
|---|---|---|
| 增资 | `capital_increase` | `--pre-money`、`--primary-amount` |
| 买老股 | `secondary_transfer` | `--fully-diluted-shares`、`--seller-shares-before`、`--transferred-shares`，及 `--price-per-share` 或 `--secondary-consideration` |
| 增资加老股 | `mixed_primary_secondary` | `--pre-money`、`--primary-amount`、`--secondary-percentage`、`--secondary-consideration` |
| 现金加股份支付 | `cash_and_share_payment` | `--total-consideration`、`--cash-percentage`、`--buyer-shares-before`、`--buyer-share-price` |
| 纯股份支付 | `share_payment` | `--total-consideration`、`--buyer-shares-before`、`--buyer-share-price` |

已明确全体原股东为卖方、无税费的示例：原股本 1000 万股，投前价值 4000 万元，投入 1000 万元。每股 4 元，转让股数 250 万股。分别运行：

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/mai-transaction-structure/scripts/calculate_transaction_structure.py" --mode capital_increase --pre-money 40000000 --primary-amount 10000000 --fully-diluted-shares 10000000 --transaction-fees 0 --currency 人民币 --unit 元
python3 "${CLAUDE_PLUGIN_ROOT}/skills/mai-transaction-structure/scripts/calculate_transaction_structure.py" --mode secondary_transfer --fully-diluted-shares 10000000 --seller-shares-before 10000000 --transferred-shares 2500000 --price-per-share 4 --secondary-consideration 10000000 --transaction-fees 0 --currency 人民币 --unit 元
```

按本次实际输入替换数字；若只有总体股本、没有卖方持股，不推定某个卖方拥有全部股份，可把“全体原股东合计”作为明确的总体比较口径，不宣称已核对个别卖方能否转让。用户只给估值而未给老股价格时，明确按同一每股估值比较这个假设。


输入充分后调用：

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/mai-transaction-structure/scripts/calculate_transaction_structure.py" \
  --mode mixed_primary_secondary \
  --pre-money 600 \
  --primary-amount 100 \
  --secondary-percentage 0.20 \
  --secondary-consideration 120 \
  --currency 人民币 \
  --unit 百万元 \
  --calculation-date 2026-08-30 \
  --input-source "用户提供，待核验"
```

程序参数是机器标识；向用户解释时始终使用“增资加老股转让”等中文交易表达。详细公式和失败规则见 `references/计算口径与证据规则.md`。

本地候选不联网、不上传输入、不写入项目资料，也不查询公开股价或监管规则。输入不足时不得编造。

## 结果怎么说

用户输入含有英文通用交易词时，先翻译为中文再输出。不得在面向用户的标题、表头、情景名或说明中回显英文通用词；公司法定名称、证券代码或必须逐字引用的文件原文除外，并在首次出现时补充中文说明。

按以下顺序输出：

1. **一句话结论**：本次结构最核心的资金与股权变化；
2. **资金去了哪里**：公司取得的增资款、卖方取得的老股对价、卖方取得的股份对价、交易费用和现金总需求；
3. **股权发生了什么变化**：买方持股、卖方持股、新发行股份和稀释；
4. **资金来源与融资缺口**：只汇总已确认资金，未知项保持待补；
5. **情景对比**：用户要求时并列两至三个结构，不堆叠过多方案；
6. **依据与边界**：列明时点、来源、完全稀释口径和待核实事项；
7. **下一步**：最多两个能继续推进的动作；
8. **收尾**：符合下方频控时才展示反馈入口。

必须明确写出：不得把老股对价写成公司融资；不得把股份对价写成现金流出。资金来源未给出时，只说“资金来源待补”，不把未知项当作零后宣称资金已经落实。

## 异常与停止计算

- 金额、股份数量或价格小于零时停止计算；
- 投前估值、完全稀释总股本或买方参考股价不大于零时停止计算；
- 受让股份超过卖方持股或完全稀释总股本时停止计算；
- 现金与股份比例合计不等于100%时停止计算；
- 股份、比例、每股价格和总对价互相矛盾时停止计算；
- 不同日期、币种或金额单位混用且无法换算时停止计算。

停止计算时用一句中文说明冲突，再列出恢复计算所需的最少信息。不得展示私有判断库、客户材料、私人关系、联系人或生产凭据。

数据保存和反馈规则见 `references/数据与反馈说明.md`。

## 简短结果优先

用户只要求算几个数字或快速核对时，结果主体只给一句结论、一张必要的小表和最多一个关键假设，正文以 250 个中文字符以内为目标（表格数字除外）。不机械套用多个章节、三项重点及三项下一步，不新增未请求的混合方案或敏感性情景。复杂问题才按前文完整结构展开。反馈或数据选择至多附加一个。
